# Инженерный режим, сервисные протоколы CAN/UDS и криптография `RSA-1024` / `SWaP` / `ODX`

[![Read in English](https://img.shields.io/badge/lang-English-blue)](engineering-and-swap.en.md) • [К оглавлению `docs/`](README.md)

В этом разделе приведены точные машинные патчи **Инженерного режима**, спецификация диагностических и калибровочных протоколов шлюза **Continental VAG MQB J533 (`3Q0 907 530 xx`, `RH850/F1L`)**, формат заливки параметрии `ZDC` и устройство криптографии **`RSA-1024 (e = 3)`** для сертификатов **`SWaP FSC v2`** и прошивок **`ODX`**.

---

## 1. Что именно меняет патч Инженерного режима (`patch-engineering`)

Команда `patch-engineering` (и соответствующий переключатель в GUI) вносит четыре обратимые правки, каждая из которых находится по уникальной машинной сигнатуре (и возвращается в 100 % заводской вид с флагом `--restore-stock`):

| № | Узел прошивки | Заводской код (`RH850`) | Инженерный патч (`RH850`) | Технический эффект |
| :---: | :--- | :--- | :--- | :--- |
| **1** | Гейт `Feature 0x80 / 0x81 / 0x83` (`CodeFlash`) | `40 0E E0 FE` (`movhi 0xfee0, r0, r1`) | `00 52 7F 00` (`mov 0, r10; jmp [lp]`) | Проверка системных инженерных разрешений сразу возвращает `0` (активно) без процедуры `31 01 03 06` |
| **2** | Фильтр адресов `CCP_CheckAddr` (`CodeFlash`) | `E0 E7 06 E3` (`cmov nh, 0, r28, r28`) | `00 00 00 00` (`nop; nop`) | Снимает блокировку адресов калибровочного сервера `ASAM CCP`: открыто чтение `CodeFlash` / `DataFlash` / `Uflash` / `RAM` и запись `RAM` на работающем блоке |
| **3** | Вход `0x07FC80FE` в `CAN RAM-Loader` (`CodeFlash`) | `D2 0D` (`be +26`) + `OTP [0x0000A167] = 0xFF` | `00 00` (`nop`) + `OTP [0x0000A167] = 0x00` | Разрешает штатный вход из приложения в загрузчик `0x6F0 / 0x6F1` по 29-битному кадру `0x07FC80FE` |
| **4** | Верификатор `FBL CheckMemory` (`Uflash + 0x342A`) | `E2 57 14 EB` (`cmov ne, 2, r10, r29`) | `00 EA 00 00` (`mov 0, r29; nop`) | Рутина `31 01 02 02` принимает любые прошивки и `.odx` с верным `App CRC-16` без заводской подписи `RSA-1024` |

После модификации `CodeFlash` автоматически пересчитывается `Application CRC-16/MODBUS` (`poly = 0xA001`) по адресу `0x0000C21C`.

## 2. Сессии диагностики UDS и алгоритмы `SecurityAccess`

На диагностическом CAN (`500 кбит/с`, запрос тестера **`0x710`** → ответ гейтвея **`0x77A`**) даже на стоковой прошивке доступны четыре сессии:

| Запрос (`0x710`) | Ответ (`0x77A`) | Сессия | Назначение |
| :---: | :---: | :--- | :--- |
| `10 03` | `50 03 ...` | `ExtendedDiagnosticSession` | Кодирование (`0x0600`), список комплектации (`0x04A3`), сервисные тесты `LIN` / `BEM` / `Wake-up` |
| **`10 40`** | `50 40 ...` | **`EOLSession` (VW End-Of-Line)** | Загрузка параметрии `ZDC` (`0x34 / 0x36`), запись сертификатов `SWaP FSC` (`0x3C01` + `0xC001`), рутины `KSCHUTZ` (`0x0567`) |
| **`10 4F`** | `50 4F ...` | **`DevelopmentSession`** | Инженерная сессия разработчика и доступ `27 03 / 27 04` |
| `10 02` | `50 02 ...` | `ProgrammingSession` | Перезапуск в загрузчик `Uflash.bin` (`0xFEDFFFF0 = 0xA5430911`) |

### `SecurityAccess` основного приложения (`CodeFlash`) — уровень `27 03 / 27 04`

На шлюзе Continental `J533` подуровень `27 01 / 27 02` **отсутствует** (возвращает `7F 27 12` `subFunctionNotSupported`). Вся авторизация в основном приложении (включая штатные сессии `ODIS`) идёт через **`Level 3` (`27 03` → `27 04`)**, который принимает два варианта ключа:

1. **Открытый сервисный логин VAG `20103` (`0x00004E87`)** — используется `ODIS` и `ContiTool` для заливки параметрии `ZDC`, активации `SWaP FSC` и конвейерных рутин в `10 40`:
   - Формула: `Key = (uint32_be(Seed) + 0x00004E87) & 0xFFFFFFFF`
   - Пример (`Seed = 12 34 56 78`): `27 04 12 34 A4 FF` → `67 04` (если `Seed == 00 00 00 00`, доступ уже открыт и `27 04` не отправляется).
2. **Инженерный уровень Continental (`0xCAFFE012`)** — разблокирует предпосылки программирования (`31 01 02 03`) и инженерные сервисы:
   - Принимает как динамический ключ `Key = (uint32_be(Seed) + 0xCAFFE012) & 0xFFFFFFFF`, так и **статический не зависящий от `Seed` пароль `CA FF E0 12`** (`27 04 CA FF E0 12` → `67 04`).

### Алгоритм `VAG SA2` бутлодера `Uflash` (`10 02` → `27 11 / 27 12`)

В сессии программирования `10 02` бутлодер проверяет ключ через байт-код-машину `SA2` (`0x010023D8`, скрипт в `0x0000A377`):

```python
def conti_j533_fbl_sa2(seed: int) -> int:
    x = seed & 0xFFFFFFFF
    for step in range(8):
        msb = (x >> 31) & 1
        x = ((x << 1) | (1 if step in (2, 7) else 0)) & 0xFFFFFFFF
        if msb:
            x ^= 0x1EDC6F41
    for _ in range(11):
        borrow = x < 0x80361423
        x = (x - 0x80361423) & 0xFFFFFFFF
        if borrow:
            x ^= 0x04000200
    return x
```

Тестовые векторы:
- `0x00000001` → `0x7DAD27A0`
- `0x12345678` → `0x7CA16271`
- `0xDEADBEEF` → `0x3AEE8BB5`
- `0xFFFFFFFF` → `0xEAE26413`

## 3. Протокол `ASAM CCP v2.1` (`29-бит CAN 0x1BFC8600 / 0x1BFC8601`) и штатный вход `0x07FC80FE`

В прошивку шлюза встроен сервер калибровки **ASAM CCP v2.1** (`500 кбит/с`, 29-битные Extended CAN ID, адрес станции **`0x0055`** Big-Endian):
- **Запрос (`CRO`, `0x1BFC8600`):** `[CMD, CTR, Byte2, Byte3, Byte4, Byte5, Byte6, Byte7]`
- **Ответ (`DTO`, `0x1BFC8601`):** `[0xFF, ERR, CTR, D0, D1, D2, D3, D4]` (`ERR = 0x00` — успех, `0x33` — адрес закрыт на стоке без `patch-engineering`).

| `CMD` | Мнемоника | Запрос `0x1BFC8600` | Описание |
| :---: | :--- | :--- | :--- |
| `0x01` | `CONNECT` | `01 <CTR> 00 55 00 00 00 00` | Открытие сессии со станцией `0x0055` |
| `0x1B` | `GET_CCP_VERSION` | `1B <CTR> 02 01 00 00 00 00` | Подтверждение версии `CCP 2.1` |
| `0x02` | `SET_MTA` | `02 <CTR> <00\|01> 00 <Addr_BE32>` | Установка 32-битного адреса в указатель `MTA0` (`00`) или `MTA1` (`01`) |
| `0x04` | `UPLOAD` | `04 <CTR> <Size:01..05> 00 00 00 00 00` | Чтение `1..5` байт из `[MTA0]` со сдвигом `MTA0 += Size` |
| `0x0F` | `SHORT_UP` | `0F <CTR> <Size:01..05> 00 <Addr_BE32>` | Однокадровое чтение `1..5` байт по адресу через `MTA1` |
| `0x03` | `DNLOAD` | `03 <CTR> <Size:01..05> <D0..D4>` | Запись `1..5` байт в ОЗУ по `[MTA0]`, `MTA0 += Size` |
| `0x23` | `DNLOAD_6` | `23 <CTR> <D0..D5>` | Запись `6` байт в ОЗУ по `[MTA0]`, `MTA0 += 6` |
| `0x07` | `DISCONNECT` | `07 <CTR> <00\|01> 00 00 00 00 00` | Завершение сессии |

### Практические операции через `ASAM CCP` (на блоке с `patch-engineering`)

1. **Чтение банка CP `#7` (`5F` @ `0xFF20C600`):**
   `CONNECT` → `SET_MTA(0xFF20C600)` → серия `UPLOAD(5)` читает шапку `55 55 55 55` и байты ключа прямо на работающем блоке.
2. **Мгновенное включение всех 13 функций `SWaP / FeC` в ОЗУ до перезагрузки:**
   Менеджер `SWaP` (`0x0007E05A`) хранит битовую маску разрешённых функций в `*(uint16_t *)0xFEDE1394` (`0x0002` — `MKE`, `0x0008` — `FPA Base`, `0xFFE0` — 11 профилей движения `FPA`). Запись слова **`0xFFFA`** (`FA FF` LE) включает сразу все 13 лицензий:
   ```text
   TX 0x1BFC8600: 01 01 00 55 00 00 00 00   -> RX 0x1BFC8601: FF 00 01 ...
   TX 0x1BFC8600: 02 02 00 00 FE DE 13 94   -> RX 0x1BFC8601: FF 00 02 ...
   TX 0x1BFC8600: 03 03 02 FA FF 00 00 00   -> RX 0x1BFC8601: FF 00 03 00 FE DE 13 96
   ```
3. **Переход в `CAN RAM-Loader` в любой момент работы:** запись `0xA4420810` (`10 08 42 A4` LE) в `0xFEDFFFF0` через `SET_MTA` + `DNLOAD` и отправка `UDS 11 01`.

### Штатный вход `0x07FC80FE` и алгоритм `Stage 1 Seed/Key` (`0x6F0 / 0x6F1`)

На блоке с `patch-engineering` подача 29-битного кадра `TX 0x07FC80FE: 84 00 00 00 00 00 00 00` при старте перезапускает МК на первый этап `CAN RAM-Loader` (`0x01000BCC`), где обмен идёт на `0x6F0 / 0x6F1`:
1. Запрос `Seed`: `30 00 00 00 00 00 00 00` → ответ `30 <S0 S1 S2 S3>`.
2. Расчёт 4-байтного ключа (`poly = 0xA001` reflected, **`init = 0x0000`**):
   ```python
   def crc16_reflected_zero(data: bytes) -> int:
       crc = 0x0000
       for b in data:
           crc ^= b
           for _ in range(8):
               crc = ((crc >> 1) ^ 0xA001) if (crc & 1) else (crc >> 1)
       return crc & 0xFFFF

   def conti_ramloader_key(seed4: bytes) -> bytes:
       s0, s1, s2, s3 = seed4
       buf = bytes([0x65, 0x96, s2, s1, 0xAC, s3, 0x53, s0])
       c1, c2 = crc16_reflected_zero(buf[0:8]), crc16_reflected_zero(buf[2:8])
       b0, b1, b2, b3 = c1 & 0xFF, (c1 >> 8) & 0xFF, c2 & 0xFF, (c2 >> 8) & 0xFF
       rem = s3 % 3
       return bytes([b1, b2, b3, b0] if rem == 0 else ([b2, b0, b1, b3] if rem == 1 else [b3, b2, b0, b1]))
   ```
   Примеры: `12 34 56 78` → `58 A0 46 90`; `A1 B2 C3 01` → `A4 94 EF F1`; `11 22 33 44` → `7D 60 50 63`.
3. Отправка `20 <K0 K1 K2 K3> 00 00 00`, затем `50 00 00 00 00 00 00 00` переводит загрузчик во второй этап (`0x0100120E`).

## 4. Заливка параметрии `ZDC` на стоковый блок (без `RSA`) и сервисные `DID` / `RID`

Обработчик загрузки параметрии `ZDC` в основном приложении (`0x0003E552` / `0x0003D558`) **не использует `RSA`** и проверяет только 4-байтный Little-Endian **`IEEE 802.3 CRC-32` (`zlib.crc32`)** в последних 4 байтах блока (`payload = body + struct.pack("<I", zlib.crc32(body))`). Поэтому любой отредактированный датасет заливается по OBD на 100 % заводской непатченный шлюз:

| `idx` | Адрес UDS (`0x34`) | Длина (`UDS_Len`) | Смещение в `Dflash.bin` | Назначение блока параметрии |
| :---: | :---: | :---: | :---: | :--- |
| `0` | `0x00000A00` | `0x0080` (`128` Б) | `0x0080 .. 0x00FF` | Базовый конфигурационный блок `ZDC` |
| `1` | `0x00000A80` | `0x0100` (`256` Б) | `0x0100 .. 0x01FF` | **`MKE`** — параметры распознавания усталости водителя (`'ZM3'`) |
| **`2`** | **`0x00002880`** | **`0x0800` (`2048` Б)** | `0x0200 .. 0x09FF` | **`FPA` (`Driving Profile Selection`)** — таблица режимов движения и кнопки `Mode` |
| `3` | `0x00003080` | `0x0400` (`1024` Б) | `0x0A00 .. 0x0DFF` | Дополнительный / гибридный энергоменеджмент |
| `4` | `0x00000B80` | `0x1100` (`4352` Б) | `0x1340 .. 0x243F` | **Основная таблица сетевой маршрутизации шлюза** (`'NC00'`) |
| `5` | `0x00003E00` | `0x012E` (`302` Б) | `0x1200 .. 0x132D` | Калибровочная таблица подсистем |
| `6` | `0x00001C80` | `0x0C00` (`3072` Б) | `0x2440 .. 0x303F` | **`BEM`** — характеристики АКБ, LIN-генератора и `Start-Stop` |

Последовательность штатной загрузки по UDS (`0x710` → `0x77A`, функция `can_upload_zdc_datasets`):

1. **Авторизация и отпечаток мастерской**: `10 40` → `27 03` / `27 04 <Seed + 0x00004E87>` (логин `20103`) → `2E F1 98 <6 Б тестера>` → `2E F1 99 <YY MM DD в BCD UTC>`.
2. **Неделимая передача и проверка каждого блока (`uninterruptible`)**:
   - `RequestDownload`: `34 00 44 <Addr_BE32> <Len_BE32>` → ответ `74 20 04 00` (`maxNumberOfBlockLength = 1024` Б).
   - `TransferData`: `36 <seq> <данные>` **строго полноразмерными блоками `maxNumberOfBlockLength - 2` (`1022` Б)** до хвоста (как в `ODIS-E`: `1022 + 1022 + ...`). Попытка дробить передачу мелкими кусками (например, по `240` байт после `74 10 FE`) отклоняется шлюзом с **`7F 36 31` (`requestOutOfRange`)** и оставляет датасет полустёртым!
   - `RequestTransferExit`: `37` → `77`.
   - **Немедленная поблочная проверка `CheckMemory` сразу после `37`**: запуск `31 01 02 EF 03 10 00` и опрос **`31 03 02 EF`** до завершения (`71 03 02 EF 02 FF FF` — **`CRC PASS`**, `00 00` — ошибка `CRC-32`). Этот вызов сбрасывает защёлку завершённой передачи в шлюзе (без него следующий `34` вернёт `7F 34 22`).
3. **Фиксация паспорта параметрии и автосогласование кодировки `0x0600`**:
   - запись `2E F1 A0` (`11` Б ASCII номера датасета), `2E F1 A1` (`4` Б ASCII версии) и `2E F1 A4` (`12` Б маски оборудования);
   - автоматическое чтение `22 06 00` (`30` байт), включение разрешающих битов всех загруженных блоков в кодировке (`2E 06 00`, без них прошивка шлюза игнорирует залитый датасет при старте!) и перезапуск `11 02`.

> [!IMPORTANT]
> При редактировании пресетов таблицы **`FPA` (`#2`)** заголовочный тег и байты года выпуска датасета должны оставаться неизменными (правятся только общие секции профилей с пересчётом хвостового `CRC-32`), иначе шлюз поднимает ошибку **`DTC 000601` (`Недостоверный набор данных`)**.

### Пошаговая подготовка `SWaP` и кодировки при записи параметрии по CAN (`v2.0.2`)

Одной загрузки таблицы `ZDC` недостаточно, если используемая функция закрыта лицензией `SWaP`: без кода `0x10000300` не работает `MKE`, а без кодов `0x10000100..0x1000010B` шлюз скрывает соответствующие профили вождения `FPA`. В мастере **«Записать параметрию по CAN»** `ContiTool` ведёт весь процесс по шагам:
1. Читает текущие активные функции шлюза (`22 3C 00`) и длинную кодировку (`22 06 00`), наглядно показывая, какие коды `SWaP` нужны выбранному датасету и какие байты `0x0600` изменятся.
2. Если нужные функции `SWaP` ещё не открыты, по выбору пользователя вызывает **`can_activate_swap`**: вычитывает родной `DataFlash` самого шлюза через `RAM-Loader`, прописывает недостающие коды `FeC` в записи `Multi-FSC` с сохранением родного `VIN` и всех существующих датасетов (`apply_dflash_swap_fecs`) и прошивает обновлённые блоки обратно через `DFLASH_FACI_STUB`.
3. Заливает блоки `ZDC` по штатному UDS (`can_upload_zdc_datasets`), согласует кодировку `0x0600`, повторно проверяет принятие функций по `22 3C 00` и предлагает стереть ошибки `DTC`.

### Основные сервисные `DID (0x2E)` и `RoutineControl (0x31)`

| Команда | Сессия / Доступ | Назначение |

| `31 01 10 27` | `10 40` + `27 03/04 (20103)` | Стендовый EOL-тест трансиверов CAN/LIN |

## 5. Криптография `RSA-1024 (e = 3)`, сертификаты `SWaP FSC v2` и подпись `ODX`

### 1. Параметры ключей `RSA-1024` на гейтвее `J533`

Обе криптоподсистемы шлюза (проверка сертификатов `SWaP` в приложении и проверка прошивок `.odx` в загрузчике `Uflash`) используют **1024-битный RSA с жёстко фиксированной публичной экспонентой `e = 3`**:
- встроенный генератор **ContiTool** подбирает 512-битные простые числа `p` и `q` (40 раундов теста Миллера — Рабина) со старшими битами `11` и условием `p % 3 == 2`, `q % 3 == 2`, чтобы `gcd((p - 1)(q - 1), 3) == 1` и модуль `N = p * q` имел ровно `1024` бита (`MSB = 1`);
- ключи сохраняются одновременно в `.json` и стандартные файлы OpenSSL `.private.pem` (`PKCS#1`) и `.public.pem` (`SPKI`).

### 2. Где хранятся публичные модули `N` (`128` байт Big-Endian)

1. **Ключ `SWaP / FeC` (`--target swap`) — синхронная замена в двух местах:**
   - в `CodeFlash.bin`: 128 байт сразу после уникального 38-байтного заголовка `00 1B 00 FF FF FF` + `(31 × 0x00)` + `03`;
   - в `DataFlash.bin` (`NvM 0x7C @ 0xDB00`): прошивка кэширует публичный модуль `SWaP` во флеш-данных! **ContiTool** обновляет 128 байт модуля по смещению **`0xDB04`**, **неприкосновенно сохраняет родной 5-байтовый аппаратный `VCRN` блока по смещению `0xDC0C`** (`DID 0x3C03`) и пересчитывает `IEEE CRC-32` (`480` байт диапазона `0xDB04..0xDCE3`) по смещению **`0xDCE4`**.
2. **Ключ загрузчика `FBL / ODX` (`--target fbl`):**
   - хранится в `Sector 5` полного 1.5-мегабайтного `CodeFlash.bin`: 128-байтная экспонента (`127 × 0x00 + 0x03`) по адресу **`0x0000A277`** и 128-байтный модуль `N` по адресу **`0x0000A2F7`**.

### 3. Побайтовая структура 171-байтного (`0xAB`) сертификата `VAG SWaP FSC v2` (`sign-fsc`)

Сертификат состоит из **43-байтного тела (`0x00..0x2A`)** и **128-байтной подписи (`0x2B..0xAA`)**:

| Смещение | Длина | Значение | Описание поля |
| :---: | :---: | :--- | :--- |
| `+0x00` | `2` Б | `11 02` | Заголовок формата контейнера `VAG FSC v2` |
| `+0x02` | `4` Б | `FeC_BE32` | Код функции Big-Endian (напр., `10 00 01 00` — `FPA`, `10 00 03 00` — `MKE`) |
| `+0x06` | `1` Б | `03` | Тип индивидуального идентификатора (`VCRN`) |
| `+0x07` | `5` Б | `VCRN[0..4]` | 5-байтовый аппаратный `VCRN` шлюза из `DataFlash @ 0xDC0C` (`DID 0x3C03`) |
| `+0x0C` | `18` Б | `VIN_17B + 0x00` | 17 ASCII-символов `VIN` + завершающий `0x00` (либо `18` нулевых байт) |
| `+0x1E` | `4` Б | `Timestamp_BE32` | Время выпуска сертификата (`Unix UTC`, Big-Endian) |
| `+0x22` | `9` Б | `00 × 9` | Поле ограничений срока действия (`00..00` — бессрочная лицензия) |
| `+0x2B` | `128` Б | `Signature_128B` | Подпись `RSASSA-PKCS1-v1_5` над хешем **`TeleTrusT RIPEMD-160`** от первых `43` байт (`DigestInfo = 30 21 30 09 06 05 2B 24 03 02 01 05 00 04 14` + `20` Б дайджеста) |

#### Пятишаговая активация выпущенного `FSC` по OBD (`0x710` → `0x77A`)

1. `10 40` — вход строго в `EOLSession` (в сессии `10 03` команда `31 01 C0 01` отклоняется).
2. `27 03` → `27 04 <Seed + 0x00004E87>` — разблокировка `SecurityAccess Level 3` (открытый логин `20103`).
3. *(Опционально)* чтение `VCRN` для сверки: `22 3C 03`.
4. `2E 3C 01 <171 байт FSC>` — запись сертификата в буфер ОЗУ `0xFEDF590D`.
5. **`31 01 C0 01`** *(строго 4 байта без встроенных данных — передача сертификата внутри `31 01` вернёт `7F 31 13`!)* → затем опрос завершения **`31 03 C0 01`** (удаление установленного кода: `31 01 C0 02 <4B FeC>`).

### 4. Подпись прикладной прошивки для `ODX` (`sign-odx`)

При проверке `CheckMemory (31 01 02 02)` штатный бутлодер `Uflash` вычисляет хеш **`SHA-1`** над конкатенацией 8-байтного Big-Endian заголовка адреса/длины и тела `FD_0DATA`:

$$\text{Msg} = \mathtt{00\,00\,C2\,00} \;\|\; \mathtt{00\,17\,3E\,00} \;\|\; \text{FD\_0DATA}_{1\,523\,200\text{ B}}$$

Команда `sign-odx` сначала проверяет корректность `App CRC-16` по `0x0000C21C` и ненулевой счётчик диапазонов по `0x0000C21E`, после чего формирует 128-байтную подпись `RSASSA-PKCS1-v1_5 (SHA-1)` (`DigestInfo = 30 21 30 09 06 05 2B 0E 03 02 1A 05 00 04 14`), готовую для вставки в тег `<FW-SIGNATURE>` контейнера `.odx`.
